# Callio — AI Receptionist (Proof of Concept)

A **backend-focused Go demo** of an AI receptionist that talks to a caller in real time, detects when a human should take over, and produces a post-call summary.

Callio runs entirely in a browser for demonstration purposes: **it does not answer real phone calls**. A small vanilla JavaScript UI simulates a caller, while a Go server handles bidirectional audio streaming, Gemini Live integration, conversation state, and call completion.

> **Scope:** A deliberately local, single-user proof of concept — no user accounts, authentication, database, cloud infrastructure, or telephony integration. It is **not intended for public internet deployment**.

## Features

- **Real-time voice conversations** with Gemini Live using full-duplex audio and WebSockets.
- **Multilingual conversation:** a configurable initial French, English, or Korean greeting; later replies follow the caller's spoken language.
- **Interruption / barge-in:** stop stale assistant audio when the caller speaks over it.
- **Live transcripts** for caller and assistant, with best-effort segment ordering and finalization.
- **Simulated human handoff:** accept, decline, or simulate no answer; the Go backend validates transitions.
- **Natural and idle call completion:** wait for the assistant's final audio to finish before closing the call.
- **Post-call structured summary** generated by a separate Gemini text model.
- **Browser-side silence filtering** to avoid continuously uploading quiet microphone frames.
- **Echo mode** for testing the audio transport without an API key.
- **Docker and native Go startup**, with no database or frontend build step.

| WebSocket | [`github.com/coder/websocket`](https://github.com/coder/websocket) | Full-duplex binary audio and JSON control frames |
| AI voice | **Gemini Live API**, [Google Gen AI SDK for Go](https://pkg.go.dev/google.golang.org/genai) (v1.26.0) | Real-time audio input/output, transcriptions and function calls |
| AI summary | **Gemini text model** via the same Go SDK | Separate structured JSON summary after a call |
| Browser UI | **Vanilla JavaScript, HTML and CSS** | No frontend framework or build pipeline |
| Audio capture/playback | **Web Audio API + AudioWorklet** | Microphone access, PCM16 conversion and low-latency playback |
| Configuration | **Environment variables**, `godotenv` | Simple local setup without a secret manager |
| Packaging | **Multi-stage Docker build** (Go + Alpine) | Small standalone image with static assets; non-root runtime |
| Testing | **Go `testing` / race detector**, Node.js built-in test runner | Backend lifecycle/adapter tests and browser-side audio unit tests |

There is **no database, Redis, message broker, Node.js backend, React application or hosted frontend**. The Go process serves both the API and the static browser files.

## Get a Gemini API key

Callio uses an **API key**, not a Google OAuth login or a service-account JSON file. The key is used only by the Go backend, both for real-time voice and for the separate post-call summary.

1. Sign in to [Google AI Studio — API keys](https://aistudio.google.com/apikey) with a Google account, and accept Google's terms if prompted.
2. Select an existing Google Cloud project or create one in AI Studio. New accounts may receive a default project/key automatically; existing Cloud projects may need to be imported under **Dashboard → Projects → Import projects**.
3. Choose **Create API key** if you do not already have a suitable key, and copy the resulting key. New AI Studio keys use Google's *auth key* format; use the new key rather than a legacy standard key.
4. From the Callio repository root, run `cp .env.example .env`, then set `GEMINI_API_KEY=YOUR_API_KEY` in the **local** `.env` file.
5. Start Callio using Docker or Go as described below. Open `http://localhost:8080`, select **Gemini Live**, grant microphone permission and start a conversation.

```dotenv
# .env — example only: replace the placeholder locally
GEMINI_API_KEY=YOUR_API_KEY
GEMINI_MODEL=gemini-3.8-live
GEMINI_SUMMARY_MODEL=gemini-3.5-flash-lite
```

Do **not** push the real key to GitHub, paste it into frontend code, or put it into a Docker image. `.env` is ignored by Git and Docker receives it at runtime via `--env-file .env`. The browser never needs to know the key. A key is **optional** for Echo mode.

## Quick start (Docker)

**Requirements:** Docker and a modern browser with microphone access. To use AI mode, you also need a Gemini API key with access to the configured models.

```bash
git clone https://github.com/alexandrevanhoutte/CallioPoc.git
cd CallioPoc
cp .env.example .env
```

For **Echo mode**, leave `GEMINI_API_KEY` empty. For **Gemini Live**, edit `.env` and enter your own `GEMINI_API_KEY`. Keep this file private.

```bash
docker build -t callio .
docker run --rm --init --name callio -p 127.0.0.1:8080:8080 --env-file .env callio
```

Open **http://localhost:8080**.

Select **Echo** (no credentials required) or **Gemini Live** (requires a working API key), click **Start conversation**, and grant microphone permission. Headphones are recommended to prevent the assistant's voice from feeding back into the microphone.

Stop the container with `Ctrl+C`.

**Why bind to localhost?** The container listens on `0.0.0.0:8080` internally so Docker port forwarding works, but the command above publishes the port **only on the host's loopback interface**. This POC has no authentication. Avoid publishing it on public or shared networks.

The image uses a multi-stage Go build, serves the bundled static web UI, and runs as a non-root user. Docker does not need Node.js or a separate frontend server.

## Run without Docker

**Requirements:** Go 1.23+ and a modern browser with AudioWorklet support. Node.js is optional and used only for frontend tests.

```bash
git clone https://github.com/alexandrevanhoutte/CallioPoc.git
cd CallioPoc
cp .env.example .env
# Optional: add GEMINI_API_KEY to .env for Gemini Live
go run -mod=vendor ./cmd/callio
```

Open **http://localhost:8080**. By default the native Go server listens only on `127.0.0.1`, and process environment variables override `.env`.

## Backend architecture

The Go backend is intentionally a **single process**. It owns the WebSocket protocol, session lifecycle, AI-provider integration, transcripts, and summary generation. The frontend is a lightweight audio test client, not a separate application backend.

```text
Browser (vanilla JS)
  | microphone / AudioWorklet
  | PCM16 mono, 16 kHz, 20 ms frames
  | WebSocket /ws/live
  v
Go HTTP + WebSocket bridge (internal/httpapi)
  | validates frames and control messages
  | owns per-connection session + call lifecycle
  | reads browser and provider streams concurrently
  | serializes outgoing WebSocket writes
  v
Provider-neutral contracts (internal/realtime)
  | VoiceProvider / VoiceSession / typed events
  v
Gemini Live adapter (internal/realtime/gemini)
  | live conversation + transcription + tool calls
  | PCM16 mono, 24 kHz audio back to browser
  v
Browser playback / transcript / handoff UI

Completed call -> finalized transcript + call metadata
               -> Gemini text summarizer
               -> call_summary WebSocket event
```

### 1. Thin transport layer

`internal/httpapi` registers the HTTP routes and bridges browser WebSocket frames to the voice provider. Browser audio arrives as **binary** frames; structured events and control commands use **JSON text** frames. The handler validates incoming audio, handles call controls, and forwards provider events to the browser.

Each live WebSocket connection owns its own `liveSession`, provider session, transcript collector, and call lifecycle. The two streaming directions run concurrently. A mutex serializes WebSocket writes, and cancellation/cleanup closes the upstream voice session and browser connection.

### Goroutines and full-duplex streaming

The `GET /ws/live` handler is the **session supervisor**. It creates one `liveSession` and one Gemini `VoiceSession` per browser WebSocket connection. Inside the handler (`internal/httpapi/live.go`), it starts **three goroutines** that have distinct responsibilities:

```text
                    One browser WebSocket connection
                                 |
                           audioLive()
                        session supervisor
                                 |
                 +---------------+---------------+
                 |               |               |
       readBrowser(ctx)   readModel(ctx)   watchInactivity(ctx)
          goroutine          goroutine         goroutine
                 |               |               |
       WS.Read / controls  voice.Receive()    time.Ticker
       voice.SendAudio()   WS.Write / events   idle checks
                 |               |               |
                 v               ^               |
           Gemini Live bidirectional session     |
                 |                               |
                 +--------- call lifecycle <-----+
```

- **Browser → Gemini:** `readBrowser(ctx)` reads each WebSocket message. Binary frames must contain exactly **640 bytes** (20 ms of mono 16 kHz PCM16). It forwards valid audio via `VoiceSession.SendAudio(ctx, frame)`. JSON text frames carry controls such as `audio_stream_end`, `accept`, `decline`, `no_answer`, `end_call` and `playback_finished`.
- **Gemini → browser:** `readModel(ctx)` continuously calls `VoiceSession.Receive(ctx)`. The Gemini adapter converts SDK responses to **provider-neutral typed events**: audio, transcripts, turn-end, interruption, handoff request and end-call request. Audio is returned as binary **24 kHz PCM16**, while metadata and commands are JSON.
- **Inactivity:** `watchInactivity(ctx)` runs a ticker, checks the last meaningful conversation activity and asks the lifecycle to finish an idle call. Continuous silent microphone input does **not** count as activity.

The two streaming goroutines report **termination/errors** through a buffered `results` channel; a `sync.WaitGroup` joins them during cleanup. That channel is **not an audio queue**: audio is forwarded incrementally inside the two loops. There is no new goroutine per audio frame, and no worker pool for voice streaming. The inactivity goroutine observes the same cancellation context and exits when the session ends.

`context.WithCancel`, `context.AfterFunc`, explicit `VoiceSession.Close()` and WebSocket closure ensure that a browser disconnect or server shutdown unblocks readers and releases resources. A closed Gemini receiver can be expected during the simulated human takeover; in that case the browser stays connected until the simulated call ends.

**Synchronization:** `writes sync.Mutex` prevents concurrent JSON and audio writes to the same WebSocket; the session `mu sync.Mutex` protects mutable completion/idle/transcript state. The `internal/call.Lifecycle` state machine independently validates allowed transitions. The Gemini adapter's `turnState` is owned by its receiving path rather than being mutated by both streaming goroutines.

### End-to-end audio flow

```text
Microphone
  -> AudioWorklet: PCM16 mono @ 16 kHz, 20 ms frames
  -> browser VoiceActivityGate (RMS + 200 ms pre-roll + 700 ms hangover)
  -> browser WebSocket, binary 640-byte frames
  -> Go readBrowser -> VoiceSession.SendAudio
  -> Gemini Live: speech detection + inference
  -> VoiceSession.Receive -> normalized EventAudio / EventTranscript / ...
  -> Go readModel -> browser WebSocket
  -> Web Audio playback: PCM16 @ 24 kHz + transcript UI
```

The **frontend**, not Go, converts microphone samples to the upload format. The Go server validates frame sizes and forwards PCM16; the Gemini adapter splits incoming model audio into approximately **20 ms / 960-byte** playback chunks. Other typed messages accompany audio on the same browser WebSocket as JSON.

**Interruption (barge-in):** Gemini can signal an interruption while an older assistant response is still queued. The adapter marks the interrupted turn, the bridge drops stale output using locally assigned turn IDs, and the browser flushes its playback queue. The voice connection remains open for the caller's next turn.

**Backpressure:** before uploading a frame, the browser checks its WebSocket `bufferedAmount` and may drop frames when the pending byte budget is exceeded. This is a small POC safeguard, not a guaranteed lossless audio transport or production-grade flow-control protocol.

### 2. Provider-independent contracts

`internal/realtime` defines `VoiceProvider`, `VoiceSession`, typed events, transcript segments, handoff metadata, and provider-neutral prompts. The concrete Gemini adapter lives in `internal/realtime/gemini`.

The HTTP bridge depends on these interfaces rather than on Gemini SDK types. A future provider could implement the same contracts without rewriting the transport or state machine. **Only Gemini is implemented in this demo.**

### 3. State-driven call lifecycle

`internal/call` enforces the call states and their valid transitions:

```text
ai_active -> handoff_required -> human_active -> completed
                   |
                   +-- decline / no_answer --> ai_active

ai_active -------------------------------> completed
```

Gemini can request a handoff or natural call end through tool calls, but **the backend owns the actual state transitions**. Human takeover is simulated: accepting a handoff closes the AI voice session, and the UI remains connected until the simulated human ends the call. There is no PSTN connection or human audio bridge.

On natural completion, the server sends `call_finishing`, waits for `playback_finished` from the browser (or finishes after a bounded fallback), then emits `call_state: completed` and generates the summary. Idle completion is supported too.

### 4. Audio streaming, concurrency, and interruptions

The browser captures microphone audio through an AudioWorklet and converts it to fixed-size PCM16 frames. A small RMS-based voice-activity gate suppresses most quiet frames in AI mode and sends an `audio_stream_end` boundary after speech.

Gemini sends audio and conversation events back through the same session. The bridge distinguishes interrupted and completed assistant turns, discards stale buffered audio after interruption, and notifies the browser to flush playback. This supports talking over the assistant without reconnecting.

Go contexts are used for cancellation and server shutdown. The server also handles `SIGINT` / `SIGTERM` and gives HTTP requests a bounded graceful-shutdown window.

### 5. Transcripts and summaries

Call transcripts are collected **in memory**, with provisional and finalized segments. Once a call completes, only finalized transcript data and relevant call metadata are passed to a separate text-generation request to produce a structured French summary. Summary failure is reported without undoing call completion.

Call metadata, transcripts, and summaries are **not persisted to files or a database**. Reloading the page or restarting the server loses them.

### Dynamic prompts and tool-driven behavior

Callio does **not** have a prompt-editor service or a database of user-specific instructions. Instead, `internal/realtime/prompt.go` defines **provider-neutral prompt builders**. Static rules are combined with a small amount of **runtime context**, so the model receives the right instructions for the current call and event.

| Stage | Source | What changes |
| --- | --- | --- |
| Live session setup | `ReceptionistInstructions` | Static English system instructions: assistant role, concise replies, caller-language matching, information gathering and when to request actions |
| First greeting | `OpeningPrompt(locale)` and `GreetingText(locale)` | Initial spoken message chosen from `fr-FR`, `en-US` or `ko-KR` at startup; later turns follow the caller's spoken language |
| Simulated handoff result | `HandoffOutcomePrompt(outcome)` | After a **decline** or **no answer**, dynamically informs Gemini of the outcome so it can continue the conversation appropriately |
| Post-call summary | `SummaryPrompt(contextJSON)` | A **new** text-model request built from finalized transcript segments, end reason and optional handoff details |

```text
Load .env
  |
  +--> greeting locale ------> OpeningPrompt(locale)
  |                                 |
  +--> static rules --------> Gemini Live system instruction
                                    |
                            caller conversation
                                    |
                     Gemini tool call: request_handoff
                                    |
                     Go validates tool args + lifecycle
                                    |
                decline / no_answer (simulated UI action)
                                    |
                       HandoffOutcomePrompt(outcome)
                                    |
                          continue live dialogue
                                    |
                             completed call
                                    |
                    finalized transcript + call metadata
                                    |
                         SummaryPrompt(contextJSON)
                                    |
                        separate Gemini text request
```

The model has two declared **function tools** in `internal/realtime/gemini/tools.go`: `request_handoff` and `request_call_end`. The model can *request* either action; it does **not** directly change Go's lifecycle or complete a phone transfer. Go validates function arguments and owns the outcome.

Examples: a `ko-KR` greeting is fixed for the **first** spoken message only; if the caller switches to French, the model is instructed to follow French. If the demo operator clicks **Decline** on a handoff, Go sends an outcome-specific instruction and the assistant can offer to take a message. When the call ends, Go constructs a new summary prompt using **finalized** transcript data; it does not ask the live voice model to summarize itself.

These prompts are **context-dependent, not automatically personalized**: there are no stored user profiles, prompt version database, retrieval system or runtime user configuration beyond the supported settings. The final behavior still depends on the model, while the Go lifecycle, tool validation and structured summary validation enforce the deterministic parts.

## HTTP / WebSocket endpoints

| Endpoint | Purpose |
| --- | --- |
| `GET /` | Static browser demo |
| `GET /health` | Basic server health |
| `GET /capabilities` | Public `status` and `live_configured` flags (no credentials) |
| `GET /ws/audio` | Echo test: binary audio round-trip |
| `GET /ws/live` | Gemini Live audio and control events |

**Wire protocol**

| Direction | Payload |
| --- | --- |
| Browser -> Go | Binary PCM16 signed little-endian, mono 16 kHz, **640 bytes per 20 ms** |
| Go -> Browser (live) | Binary PCM16 signed little-endian, mono 24 kHz; chunk sizes may vary |
| Either direction | JSON text events for transcripts, interruptions, handoff, completion, errors, and summary |

Examples of JSON controls sent by the browser: `{"type":"accept"}`, `{"type":"decline"}`, `{"type":"no_answer"}`, `{"type":"end_call"}`, `{"type":"audio_stream_end"}`, and `{"type":"playback_finished"}`.

**Note:** The server validates protocol messages, but the service intentionally has no authentication or per-user authorization.

Copy `.env.example` to `.env`. Process environment variables take precedence over the values in that file.

| --- | --- | --- |

**Security:** Never put API keys in browser JavaScript, Docker build arguments, commits, issues, or logs. `.env` is ignored by Git and excluded from the Docker build context; inject secrets at **runtime** with `--env-file` or environment variables.

## Go dependency vendoring

Go dependencies are committed in `vendor/` (including `vendor/modules.txt`), so running the Go application, tests and Docker build does not require fetching modules from the network. A **Go 1.23+ toolchain must already be installed** for local commands. The Docker build still needs access to its base images and Alpine packages unless those are cached.

With Go 1.14+, the toolchain normally selects the vendor tree automatically when the `go.mod` directive and `vendor/modules.txt` are compatible. This project uses `-mod=vendor` explicitly so missing/out-of-sync vendored files fail immediately.

To update or add a dependency (network required for this maintenance step):

```bash
go get example.com/module@version
go mod tidy
go mod vendor
git add go.mod go.sum vendor/
```

Always commit updated `vendor/` together with any `go.mod` / `go.sum` changes. Avoid editing files inside `vendor/` directly. Vendoring makes the repository larger, but supports reproducible and offline Go builds.

## Deliberate trade-offs and limitations

This project demonstrates **backend architecture and real-time streaming**, not a production telephone service.

- **No users or authentication.** Single-user local playground; no identity, login, authorization, or account isolation.
- **No database or persistence.** Session state, transcripts, and summaries are ephemeral.
- **No real phone number or PSTN integration.** Browser microphone replaces a telecom provider; handoff and takeover are simulated.
- **No deployment infrastructure.** No Kubernetes, queues, distributed workers, load balancing, or horizontal scaling.
- **One AI provider.** Interfaces allow replacement, but Gemini is the only working adapter.
- **Prototype-grade audio activity detection.** RMS thresholds can misclassify quiet speech or background noise; automatic transcription and language switching are best effort.
- **Not hardened for untrusted traffic.** No rate limiting, authentication, production observability, or real-world consent/retention workflow.

If extending this to a production service, the first steps would include authentication, explicit consent and data-retention policies, robust telephony integration, persistent call records, and appropriate abuse controls. Live audio and finalized transcripts are sent to the configured Google models; do not test with sensitive conversations without considering privacy requirements.

## Troubleshooting

- **No AI option?** Check `GEMINI_API_KEY`, restart the process/container, and inspect `GET /capabilities`. The live model must be available to your Google project.
- **Microphone unavailable?** Use `http://localhost:8080` with a supported browser and grant microphone permission. Remote HTTP addresses may not be secure browser contexts.
- **Assistant silent or repeatedly interrupted?** Try headphones to prevent playback from reaching the microphone. Review **Advanced** audio counters and browser console output.
- **Docker port not reachable?** Use `-p 127.0.0.1:8080:8080` and keep the container's `CALLIO_BIND_HOST=0.0.0.0` default.
- **Need a different host port?** Use `-p 127.0.0.1:9090:8080` and open `http://localhost:9090`.
- **Need a different container port?** Set `PORT` in `.env` and update the right-hand side of the `-p` mapping accordingly.

## Backend logging

Callio writes structured JSON logs to stdout through an application-owned
`internal/logging.Logger` interface. The `slog` adapter is private to
`internal/logging/`; other packages must not import `log/slog` directly.

Set `LOG_LEVEL` in `.env` to `debug`, `info` (default), `warn`, or
`error`. Unknown values fail startup with a configuration error.
Each service holds and reuses its own logger, tagged with a component:

```go
type Service struct {
    l logging.Logger
}

func NewService() *Service {
    return &Service{l: logging.For("example")}
}

func (s *Service) Start() {
    s.l.Info("service started", "state", "active")
}
```

Use `logging.L()` for the root logger and `logging.For("component")`
for a component logger. `With("key", value)` returns a derived logger
without changing its parent. Tests can use `logging.New(writer, "debug")`
or inject a fake `logging.Logger` implementation. The output format and
log level are configured once in `logging.Init(...)`, so a future switch
away from `slog` requires changing only the logging kit. Never log API
keys, audio payloads, full transcripts or caller personal details.
